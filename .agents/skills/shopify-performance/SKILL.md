# Shopify 性能优化

以用户本轮要求确定交付：解释数据、定位原因、实施优化或验证收益。最新用户要求与仓库 AGENTS.md 优先；历史案例、旧任务清单和本技能都不能扩大当前范围，也不能替当前页面预设根因。

## 按任务选择流程

- **分析或方案评估**：解释已有数据，给出证据、原因假设、优先级和下一步。分析结论是本轮交付，不要求为了产出代码而修改主题，也不默认接续旧优化任务。
- **实施优化**：复用适用证据，完成已授权的修改和必要局部检查。有依据的候选不必重建基线；原因未明时先完成能区分候选的定向分析。
- **新增测量或发布核验**：按当前明确要求采样。开发阶段默认不新跑 Lighthouse、PSI 或成套前后测；读取、解析、重算用户提供或已有的 trace、报告及响应头属于分析，不是新增采样。

## 从数据定位主要等待

- 先区分单次 trace、Lighthouse 观测/模拟数据与 CrUX/RUM 聚合数据。核对可取得的 URL/参数、导航、主题/模板版本、设备、网络/CPU、缓存及统计日期；缺失项标为未知，不用设备名称推断完整测试条件。不同来源结论冲突时说明适用范围，不拼接耗时或相加各段 P75。
- 大型 trace 用程序建立索引、关联事件并输出有界摘要；按问题逐步展开，不向上下文倾倒完整 JSON、全部网络事件或内嵌源码。先定位目标导航/frame 及其最终有效 LCP 候选，再关联 nodeId、资源 URL、requestId 和目标主线程；标识结合进程/frame/时间使用，避免混入 iframe、其他导航或 LCP 之后的任务。
- 对图片 LCP，还原 TTFB、资源加载延迟、加载时长、元素渲染延迟；保留事件/字段来源、单位和导航起点，并检查分段能否解释总 LCP。主文档优先核对响应 timing，不把单个 ResourceSendRequest 事件时间当成网络起点；早期响应、重定向、文本候选或缺字段时说明口径和限制，不硬套图片公式或填零。主题维护了 LCP 指标定义时，按其记录核对测量口径。
- 检查实际输出与请求：preload 是否命中最终资源、发现时间和优先级、loading 属性、响应 MIME/传输体积、缓存以及显示依赖。已有措施不能重复推荐；扩展名、源码声明、图片 onload 或资源完成不等于实际格式、生效行为或 LCP 绘制。
- 沿占主要等待的阶段追因：TTFB 高时看请求/响应和服务端证据；资源发现晚时看 HTML 到达、解析和发起链；加载慢时看排队、响应等待与传输；显示晚时看可见性、CSS、解码、初始化和主线程。服务端 render 耗时只能定位调查方向，具体 Liquid 文件需进一步归因；父子事件或 Server-Timing 项不能未经确认就累加。
- 每个主要候选说明“观测事实 → 原因假设 → 支持/反对证据 → 下一步区分方法”，并标明置信度或证据缺口。时间重叠、请求多、代码大都不能单独证明 LCP 因果；一次 trace 的主因不能自动推广为真实用户 P75 的主因。定位源码时，优先参考主题维护的加载路径。缺少记录时，从当前页面的模板、section 和 layout 追溯请求，并核对采样版本与当前代码。
- 按对目标等待的证据、可减少的成本和实施风险排序。补充分析应能改变候选排序、实现或验证方式；方向已清楚就推进当前目标。证据不足以定位具体代码时指出最小缺口，不以容易完成的微优化替代主要问题，也不要求每次都跑完整审计。

分析输出以简短证据表和优先级结论为主：数据范围、LCP 元素/资源、阶段耗时、已有措施、已证实事实、主要假设及下一动作。未知值保留，收益估计说明依据；无需逐条复述全部事件。

## 接续与实施

- 进入源码实施前检查 Git 状态及相关差异，保留用户已有改动。只有接续既有任务时才读 HANDOFF 和其链接的当前清单；新问题从当前证据和目标源码出发，历史报告按候选需要读取。
- 沿用用户原始目标和范围。小改动可以分批交付，但不能代替页面分阶段就绪、商品区块整体减负等尚未完成的目标；一批检查通过后继续已授权的下一项。
- 优化 LCP 时，优先实施有证据能缩短目标访问中 LCP 绘制前主要等待的改动。若不同样本指向不同瓶颈，说明各自适用的条件和会改变候选排序的证据缺口。若缺口会改变实施选择，先查能回答该问题的现有源码、记录或已授权的预览。可在当前范围内完成的定位、改动和验收连续做完，中间发现作为进度更新。
- 候选收益小、不稳定或有回退时，先对该候选作出取舍。若原任务还有值得做的已授权工作，继续推进；若证据已足以决定放弃剩余候选，可以这个结论收尾。若唯一能改变决定的下一步需要额外权限或数据，说明已查过什么、最少还缺什么，以及它会改变哪个决定。
- 修改前说明影响哪段等待、要减少什么服务端渲染、请求、解析、初始化或布局工作，以及受影响的消费者。沿用主题现有的 Liquid、CSS 和交互模式，用可独立审查的改动保留原业务。
- 主候选需说明影响哪段用户等待、预期收益量级为何值得优先处理；复用已有源码和证据，量级未知就明确未知，不为此新增采样门槛。
- 微优化可顺手保留，但不能替代主要候选或原目标；主要瓶颈受 App、权限或业务限制时，明确阻碍并继续其他已授权且有价值的工作，不以更多小项代替整体完成。
- 一次实验只改变一个主要因素；分别说明资源/计算减少、用户等待改善和整页评分改善，不用请求消失或人为延迟实验代替正常访问的提速证据。
- 根据实际依赖判断范围。删除重复库前核对提供者、版本、执行顺序及复用页面；不能只因组件自身没调用该库就删除。尽量限制目标模板，避免无条件影响其他消费者。
- 主图已下载但未显示时检查可见性、样式与初始化；CLS 位移对象不等于触发源。不要盲目继续压图、加 preload、写死高度或拆公共 CSS。
- 当额外证据不会改变当前决策时停止扩展分析或采集；仍有会影响实现的矛盾时先澄清，不能仅因已有一个候选就停止。分析工具失败需说明未能验证的结论；独立且有依据的已授权代码工作可继续。

## 开发阶段的必要检查

只检查实际改动和直接依赖。优先语法、依赖顺序及相关局部逻辑；按具体风险选择必要预览，不自动展开全部断点、全购买流程、所有消费页或性能基准。用户已要求浏览器验收留到发布后时，记录待验项，继续本地实施。

- 重复引用、解析或 DOM 写入：核对目标工作确实减少，原有消费者和状态更新仍成立。
- 改变布局、初始化时机或媒体来源：针对改变的分支检查首帧/接管、实际断点或切换行为；未触及的菜单、图库、订阅等不附加完整回归。
- 改变购买、变体或视频行为：检查受影响的状态和依赖；核心分支无法验证则明确保留待验状态，不能保证零 bug 或称为可发布。
- Theme Check 如有必要，只检查变更及必要依赖；报告退出码、新增与既有问题，隔离环境缺依赖不当作源文件回退。不为已有全仓问题反复跑检查。

源码或必要局部检查已确认直接改进，且没有已知回退时可保留低风险候选，注明整体性能尚未证实。页面分数未达标、缺少统计证明或单次指标波动不能单独决定撤回；候选明确无效或造成可归因回退时，只修复或撤回本轮对应改动。保留用户原有差异。

## 发布后与明确要求的测量

用户确认发布后核对正式版本和受影响行为，按要求使用 PSI。开发期只有用户明确要求测量时才进入此流程；不从旧方案自动继承前后各三次或保护页基线。

测量只回答当前问题，复用适用证据；样本数随用户要求和决策需要确定。失败先判断是否值得重试，不连续补批次；慢样本保留。没有同条件基线或充分样本时如实记录限制，不能承诺稳定提速。指标不足不会自动阻塞其他已授权实施。

实际测量时参阅[测量口径与环境核对](references/measurement.md)。主题入口提供历史案例时，可按当前待验证的机制选读。

## 业务与权限

- 当前暂停的页面、第三方策略和业务范围继续暂停。应用、分析和同意管理工具的调整沿用当前明确授权，不因性能任务自动扩大；第三方受阻时继续可独立实施的主题内工作。
- 预览有必要时使用用户确认的有效入口，核对目标版本；无入口只影响依赖预览的检查，不暂停独立源码工作。开发同步、Git提交和正式发布是不同操作，遵循当前授权。
- 必要且已获授权的测试加购只恢复本次增量。按 variant、selling plan、properties 和数量识别商品，不能只靠变化的 line key；不清空原购物车、不提交订单。绑定条款、真实登录、订阅及平台收数未验证时明确列出。
- 本技能不额外授予建分支、提交、发布、后台配置或多代理权限。

## 交付与进度

按本轮目标交付。分析任务报告已定位的主要等待、证据强度、尚不能归因的部分及下一动作；实施任务报告保留修改、解决的具体工作、检查结果、剩余实现和待上线验证项。诊断完成、代码完成、直接成本减少、功能通过和整体指标改善分别表述，不能互相替代。

以原始目标为分母，不用自行选定的几个小改动宣布整体100%。没有可核实分母就列实际完成项；只分析时明确未修改代码即可。实施目标未完成时继续已授权且有依据的工作，采集或报告数量不能替代优化进度；阻塞项列具体原因。

需要跨轮接续的实施任务只维护一份当前清单，HANDOFF 简短链接状态和下一动作；一次性分析不自动创建任务台账。历史方案明确归档，只有需要解释决策的新证据才写报告，不同步复制整套采样记录。清理任务临时测试代码；docs 被忽略时说明仅本地保存。
