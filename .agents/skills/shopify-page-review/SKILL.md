# Shopify 页面验收

本技能的职责限于验证。按已确认的预期判断是否通过，发现异常时记录现象、复现条件和证据。根因排查、修复方案及主题代码或配置修改属于独立开发任务。

## 1. 列出验收项，等用户确认

根据用户需求、相关 Git diff 和实际模板配置，定位页面及 section 实例。共享代码按影响范围选代表页面并说明理由。整页验收覆盖主要区块和核心用户流程。用户只要求样式或功能时，按指定范围拟定计划。

先向用户列出**这次验哪里、怎么验、哪里需要补充**。分别列出样式项和功能项，为每项起一个稳定的短编号或唯一名称，写清这些信息。

| 检查项 | 页面或区块、设备与初始状态 | 操作 | 预期结果与判断依据 |
|---|---|---|---|
| 样式 S1 · 窄屏规格面板 | PDP，约定的手机宽度，面板关闭 | 展开并滚到最后一个规格 | 每项完整可读且可点选。若指定设计稿，同时与对应 frame 核对 |
| 功能 F1 · 切换后加购 | PDP，记录购物车中该规格的原数量 | 切到指定规格，选 1 件并点击一次加购 | 抽屉反馈与所选规格一致，该商品行比操作前多 1 件 |

按实际任务决定检查项和宽度。写明预览、样式参考、测试数据和流程终点。指出缺失信息影响哪一项，信息齐全时也请用户确认范围。**发出计划并获得用户对当前计划的明确确认后，才打开或操作页面。** 拟定计划时可以读取相关本地代码和用户提供的材料。若新增页面、流程或更换基准，先更新计划并请用户确认。用户按原计划补齐链接或数据并明确同意执行时，直接继续。计划内的复测按约定条件触发。新增复现路径或测试条件时，先记录观察并请用户确认是否追加。

## 2. 核验环境

确认后优先使用 Ego Lite 的 `ego-browser` 技能。如果它不可用或无法提供本次需要的独立会话，使用当前环境中符合条件的其他浏览器。

正式站验收（包括用作线上对照）直接使用独立浏览器会话，隔离主题预览 Cookie。打开后先核对 Shopify 主题元数据里的 `theme.role` 为 `main`，并记录主题 ID。预览验收优先复用匹配的预览，若指定主题 ID，核对实际 ID。对照线上时，两端分别核验身份。预览主题可通过 Shopify 主题元数据或预览工具栏核对。地址栏里的预览参数可能在重定向或切换规格后消失。重新导航后如有疑问，再核实当前主题。

样式和功能验收都先核对实际打开的店铺、页面、商品或 section 及视口宽度。同时验收桌面和手机时，各用独立标签页，加载前设好对应视口，并行检查。涉及购物车等共享业务状态时，为各端使用独立会话，再并行执行。条件无法确认时，说明受影响的项，继续其他已确认且可独立执行的项。

## 3. 按计划逐项执行

合并可以连续完成的浏览器操作和证据采集，截图聚焦于能说明结论的状态。

**样式。** 每个区域按用户指定的依据对照，同时实测与本项有关的可见性、可读性和可操作性。

| 可用依据 | 如何判断 |
|---|---|
| Figma | 对齐节点、frame 宽度和状态。只有桌面稿时，可按计划在手机实测响应式表现。 |
| 线上页面 | 对齐区块、视口、市场、语言、规格和交互状态，记录本次允许变化的部分和影响比较的条件差异。 |
| 截图 | 核对截图覆盖的区域、宽度和状态。不同区域可以分别采用设计稿或线上基准。同一区域有冲突时请用户确定依据。 |
| 无参考基准 | 以可观察的表现判定。例如使用页面现有的长规格名，检查换行、滚动到底、点选及选中态。若任务还要求判断设计一致性，仅该对照结论待验。 |

在约定的宽度和相关断点两侧，实际触发滚动、展开、切换或固定栏出现等状态。遇到疑似溢出或遮挡，尝试用户的实际操作，用截图、元素边界或点击命中位置说明影响。区分组件内预期的横向滚动与整页溢出。对照截图应使用相同状态。用户在加载期间已能触发的问题也记录当时的表现。

**功能。** 从约定的初始状态通过前台控件操作，观察用户看到的反馈和最终业务状态。按本次影响覆盖边界和恢复路径，例如售罄后切回可售规格。涉及键盘或主题编辑器时，按计划检查焦点、存量和缺省配置、section 重载或重复初始化。同一操作可为多个已确认的检查项提供证据。

**加购。** 在同一测试会话按以下顺序核对。

1. 点击前记录所选 variant、购买数量及目标商品行原数量（无该行为 0）。同一 variant 可能因商品属性、订阅方案等分行，必要时记录行属性和行键。
2. 点击一次。观察抽屉或购物车页的反馈，等购物车更新后读回明细。确认实际 variant、行属性及数量，预期为原数量加本次购买数量。可从界面或同一会话的 Shopify 购物车明细读取。抽屉打开、请求成功或总件数变化只是过程证据。
3. 遇到超时或反馈冲突，先读回购物车并确认前一次操作已结束，再决定是否复测，避免重复加购。结束时只撤销能归因于测试的数量变化，核对原有商品行及数量。发现其他会话改动或无法确定归属时，保留现场并说明。

**复测。** 每个已发现的异常在已确认的条件内只做一次针对性复测，聚焦受影响的视口和触发步骤。复测结束或超时后记录结果，继续其余验收项。将复测结果追加在原验收项下，保留首次操作、预期、实际和证据，记录复测前的真实状态及条件变化。首次确实失败、随后成功时，仍记为「发现问题，复测通过」。若首次因环境不对或工具未触发操作而未完成，在记录中说明，再按有效尝试判定。涉及下单或提交外部数据时遵循已确认的流程终点。

## 4. 首句给出页面结论

最终回复以一句加粗的判断开头，写明页面、已确认的验收范围及结果。把环境说明、截图和操作记录放在结论之后。按本次实际结果选择首句。

- **有问题**。任一验收项出现已确认的异常，先点明最影响使用的一项。即使随后复测通过，也保留首次失败，例如「TITAN PDP 桌面加购有问题，首次点击后购物车为空，复测通过。」
- **暂时无法确认是否正常**。尚无已确认的异常，但仍有待验项时，直接说清缺哪一项，例如「TITAN PDP 手机加购正常，桌面加购待验。」
- **正常**。已确认的验收项全部通过时，说明通过的范围，例如「TITAN PDP 本次检查的规格切换和加购均正常。」针对历史问题的复验可写「本次桌面首次加购正常，空购物车问题未复现。」

首句之后按原编号或名称对应每个验收项。通过项可以合并为一行，只有一项且首句已覆盖时，将编号并入首句即可。优先补充异常或待验项，写清触发条件、实际影响或缺失条件。不同设备结果不一致时注明设备。复测写在原项下。截图、购物车前后数量、测试状态恢复情况等证据按需附在最后。
